# 非主窗口快捷助手调研与设计

更新时间：2026-07-27

本文将需求收敛为 Windows 端三个全局快捷键、一个统一浮层入口：截图、划词、普通呼出。浮层只保留一个输入栏和一块自动向上/向下展开的回复区；配置、历史查看和记录管理全部放在 WePChat 主窗口。

Kivio 仅用于验证技术路径。其仓库声明为 GPL-3.0，WePChat 应独立实现，不直接复制代码。

## 1. 产品边界

### 三个快捷键

| 快捷键 | 输入来源 | 打开后的行为 |
| --- | --- | --- |
| 截图 | 用户框选的屏幕区域 + 自动 OCR 文本 | 显示截图缩略图并聚焦统一输入栏 |
| 划词 | 前台应用当前选中文本 | 显示“已选文本”来源状态并聚焦统一输入栏 |
| 呼出 | 无预置内容 | 在鼠标附近直接显示统一输入栏 |

三个入口必须创建或复用同一个 `quick` 浮层窗口，不能再拆成截图问答窗、翻译窗和普通问答窗。

### 一个输入栏

不增加“问答/翻译/OCR”模式页或额外快捷键。由输入内容和当前来源决定动作：

- 截图或划词后，输入为空直接回车：提取文字。截图返回 OCR 文本，划词返回原选区文本，不调用 LLM。
- 输入内容等于“翻译”、`translate` 或 `/translate`：翻译当前 OCR/选区文本。
- 其他输入：将它作为针对当前截图、选中文本或普通上下文的问题发送给 LLM。
- 回复完成后可继续在同一个输入栏追问；`Esc` 隐藏浮层，再次按当前快捷键也可切换隐藏。

这套规则让“提取文字”保持本地、快速、零费用；翻译使用干净文本；只有真正的问题才需要视觉模型或普通 LLM。

## 2. 浮层交互

浮层默认固定宽度，输入栏是位置锚点。来源只以紧凑图标/缩略图表示，不显示第二套工具栏：

```text
            回复区（上方空间更大时）
        ┌──────────────────────────┐
        │ 流式 Markdown / 复制 / 停止 │
        └──────────────────────────┘
        ┌──────────────────────────┐
        │ 来源  唯一输入栏       发送 │  <- 锚点不移动
        └──────────────────────────┘

        ┌──────────────────────────┐
        │ 来源  唯一输入栏       发送 │  <- 锚点不移动
        └──────────────────────────┘
        ┌──────────────────────────┐
        │ 流式 Markdown / 复制 / 停止 │
        └──────────────────────────┘
            回复区（下方空间更大时）
```

布局规则：

1. 以鼠标所在显示器的 work area 计算输入栏位置，避开任务栏和屏幕边缘。
2. 先尝试向下展开；下方不足时向上；两侧都不足时选空间更大的一侧并限制回复区高度。
3. 向上展开时同时增高窗口并上移窗口原点，保证输入栏的屏幕坐标不跳动。
4. 回复区设最大高度并内部滚动；流式增量不得持续改变外窗高度。
5. 截图选区结束后再显示浮层，避免浮层进入截图。
6. 浮层 `always_on_top + skip_taskbar + decorations=false`，但不出现在 Alt+Tab；隐藏主窗口不影响它工作。

建议状态机：

```text
hidden -> acquiring_source -> ready -> generating -> result
   ^             |             |          |
   +-------------+-------------+----------+-- Esc / toggle
```

每次打开分配 `generation_id`。旧请求的事件若 id 不匹配必须丢弃，避免快速关闭、重开后上一轮流式内容写进新记录。

## 3. 三条处理链

### 截图

1. 快捷键触发后记录鼠标所在显示器和 DPI，隐藏现有浮层。
2. 创建透明全屏选区覆盖层，支持拖拽、取消和跨负坐标显示器。
3. 将逻辑坐标按目标显示器 scale factor 转为显示器局部物理像素，再从屏幕图像裁剪。
4. 立即在后台运行 Windows OCR，并打开统一浮层；OCR 完成前输入栏仍可输入问题。
5. 提取文字直接返回 OCR；翻译仅发送 OCR 文本；问答优先发送原图 + OCR 文本，模型不支持视觉时降级为 OCR 文本问答并明确提示。

Windows 实现可采用 Kivio 已验证的组合：`xcap` 负责屏幕捕获，`Windows.Media.Ocr.OcrEngine` 负责系统 OCR。OCR 需要处理系统最大图片尺寸，超限时等比缩小后识别。

### 划词

必须在创建或聚焦浮层之前获取前台选区，否则焦点会切到 WePChat：

1. 首选 Windows UI Automation：获取 focused element，读取 `TextPattern.GetSelection()`。
2. UIA 明确返回空选区时直接结束，不发送 `Ctrl+C`，避免系统提示音。
3. UIA 不可用时才走剪贴板兜底：保存原文本、等待快捷键修饰键释放、模拟 `Ctrl+C`、比较 clipboard sequence number、读取新文本、恢复原文本。
4. 剪贴板原内容不是文本时不能用空字符串覆盖；恢复失败只记录诊断，不应把旧内容误当成选区。

浏览器、Electron、自绘编辑器对 UIA 支持不一致，因此两条路径缺一不可。

### 普通呼出

不采集屏幕或剪贴板，直接在当前鼠标附近打开输入栏。它与另外两个入口共用模型、提示词、流式渲染、上下文和历史存储。

## 4. 上下文规则

设置只提供两个字段：`启用上下文` 和 `上下文条数`。

- 关闭：每次只发送当前来源和当前问题。
- 开启：追加最近 N 个已完成的快捷助手问答，N 建议限制为 `1..20`。
- “一条”定义为一个完整的 user + assistant 交换，而不是单条数据库 message。
- 当前截图原图可以发送；历史截图不得再次发送二进制，只携带其 OCR 文本、问题和答案，避免隐私泄漏和 token 激增。
- 提取文字不使用上下文；翻译默认也不使用历史上下文，避免前文污染译文。上下文仅作用于问答和追问。
- 拼装后仍要服从当前模型的 context window，超限时从最旧交换开始裁剪。

## 5. 主窗口

### 快捷助手入口

在主导航增加“快捷助手”入口。进入后沿用当前主窗口的列表 + 内容布局：

- 左侧栏按更新时间列出记录，区分截图、划词、普通问答图标。
- 支持搜索、置顶、重命名、删除和清空记录。
- 点击记录后在右侧查看完整来源、OCR/选区文本、问题和回复；截图记录可查看原图。
- 浮层本身不放历史下拉菜单，避免唯一输入入口再次变复杂。

### 设置

在设置导航增加“快捷助手”，首版只包含：

- 启用开关。
- 截图、划词、普通呼出三个快捷键录制器，并显示重复/系统占用错误。
- 供应商和模型选择；截图问答选到非视觉模型时显示降级说明。
- 一个可编辑的快捷助手 system prompt。
- 启用上下文开关和上下文条数。

OCR 引擎、翻译目标语言、回复方向等先采用自动策略，不在首版暴露额外设置。

## 6. 数据设计

复用现有 SQLite `sessions/messages` 数据模型和迁移方式，但使用固定在 app data 的 `quick-assistant.db`，不使用会随 workspace root 切换的 `wepchat.db`，也不采用 Kivio 的 `localStorage + 最多 20 条`方案：

- `sessions.mode = "quick"`。
- `sessions.meta_json` 保存 `sourceKind`、`sourceText`、`screenshotPath`、`thumbnailPath`、`sourceApp` 和动作类型。
- `messages` 保存统一浮层内的多轮 user/assistant 消息，流式结束后再提交最终内容。
- 截图文件放在受控的快捷助手资源目录，记录删除时同步删除原图和缩略图；启动时清理无数据库引用的孤儿临时图。
- 沿用 `pinned`、更新时间排序和级联删除；可补 `sessions(mode, updated_at)` 索引。

快速记录是应用级历史，数据库和截图资源都固定在 app data，不跟随项目工作区切换。

## 7. WePChat 改动面

后端建议新增：

- `quick_assistant.rs`：浮层状态、快捷键分发、上下文查询、请求 generation 管理。
- `screen_capture.rs`：显示器枚举、冻结帧和区域裁剪。
- `selection_capture.rs`：UIA + clipboard fallback。
- `windows_ocr.rs`：WinRT OCR。
- `quick_history.rs`：记录和截图资源生命周期。

前端建议新增独立的 `quick.html`、`quick-assistant.js`、`quick-assistant.css`，共享现有 `api.js`、Markdown、主题和供应商数据。不要继续堆进当前体积已经较大的 `app.js`。

依赖与权限至少包括：

- `tauri-plugin-global-shortcut`。
- `xcap`、`arboard`，以及 Windows UI Automation、Input、Clipboard、WinRT OCR 所需 features。
- Tauri capability 增加 `quick` 和截图覆盖窗口，并只授权实际需要的 window 命令。

应用启动时注册快捷键，保存设置后原子式重注册：新组合全部注册成功后才替换旧组合；失败时保留原快捷键。真正退出时注销快捷键、取消流请求并清理临时截图，托盘驻留期间继续可用。

## 8. 从 Kivio 借鉴与舍弃

值得借鉴：

- `shortcuts.rs`：UIA 读取选区、clipboard sequence number、等待修饰键释放和恢复剪贴板。
- `capture_geometry.rs`：多显示器、负坐标和混合 DPI 的逻辑/物理坐标映射。
- `windows_ocr.rs`：Windows 系统 OCR 和超大图片缩放。
- `Lens.tsx` 的回复方向计算：下方、上方、较大侧三段式选择。
- 浮层窗口复用、临时 Escape 快捷键、旧流事件 generation 隔离。

不应照搬：

- 截图翻译、划词翻译、Lens 问答分成多个窗口和多个快捷键。
- `Lens.tsx` 将截图、标注、翻译、历史、搜索和聊天堆在一个近 3000 行组件里。
- 浮层内再放历史菜单；WePChat 的历史应回到主窗口侧栏。
- 历史只存 localStorage 且固定 20 条。
- 截图标注、原位覆盖翻译、联网搜索和“发送到另一个聊天窗口”等超出本需求的能力。

## 9. 实施顺序

1. 全局快捷键、单一 `quick` 窗口、普通呼出和上下自适应回复。
2. UIA + 剪贴板划词链路，完成问答/翻译/提取三种行为。
3. 多显示器截图选区、Windows OCR、视觉模型降级。
4. SQLite 快捷记录、主窗口侧栏与记录管理。
5. 设置页模型、提示词、上下文和快捷键录制。

## 10. 最小验收

- 三个快捷键在主窗口隐藏、最小化和托盘驻留时都可用，且无终端窗口闪现。
- 同一快捷键重复按可关闭浮层，三个快捷键之间切换不会残留上一种来源。
- 浏览器、记事本、Office/Electron 应用的划词至少一条捕获路径可用，原剪贴板文本可恢复。
- 100%、125%、150% 缩放和带负坐标的多显示器截图范围准确。
- 截图提取不调用 LLM；翻译只发文本；视觉问答在非视觉模型下正确降级。
- 输入栏在回复向上/向下展开时屏幕位置不跳，回复过长只在内部滚动。
- 上下文开关和 N 条限制真实改变请求；历史截图不会作为旧上下文再次上传。
- 删除记录同时删除截图资源；应用异常退出后孤儿临时图可在下次启动清理。
